# A2UI в Dashboard, ClientNative и TUI

Дата: 2026-10-27. Статус: все этапы v1 реализованы в текущем Draft PR #75 поверх базового PR #74. Подключены Core actions, Dashboard, ClientNative, TUI и first-party скилл `sloppy/a2ui`. Итоговая проверка и её ограничения записаны в [карте поставки](../tbd/decompositions/2026-10-27-a2ui-clients.md).

## Продуктовое решение

A2UI даёт агенту возможность создавать интерфейс для конкретного шага задачи прямо в разговоре. Пользователь заполняет поля, сравнивает варианты, выбирает результат и продолжает работу без ручного пересказа значений агенту.

Первая аудитория — пользователи Sloppy, которые ведут задачи, исследуют варианты и запускают работу через агента. Подтверждённый пользователем приоритет v1: **формы и выбор вариантов**, то есть **сбор вводных → выбор → продолжение задачи**. Решение зафиксировано 2026-10-27; отчёты и мини-инструменты остаются следующими итерациями.

Интерфейс появляется, когда он экономит действия или помогает проверить данные. Для короткого ответа остаётся обычный текст. Пользователь всегда может ответить текстом вместо заполнения формы.

## Что предложить пользователям

| Сценарий | Пример | Польза | Очерёдность |
| --- | --- | --- | --- |
| Собрать вводные | Бриф задачи: цель, ограничения, платформа, пожелания | Несколько уточнений за одно заполнение | v1 |
| Выбрать вариант | Агент сравнил три подхода; пользователь выбирает один и задаёт ограничения | Решение связано с конкретным вариантом, без неоднозначного «бери второй» | v1 |
| Проверить перед продолжением | Отредактировать параметры, выбрать пункты плана, отправить агенту | Видно, с какими значениями агент продолжит работу | v1 |
| Исследовать результаты | Список найденных задач, вакансий, файлов или источников с фильтрами и выбором строк | Не нужно разбирать длинный текст и копировать идентификаторы | После v1 |
| Работать с отчётом | Таблица и график; выбор периода, источников и детализации | Можно задать следующий вопрос о выбранной части данных | После v1 |
| Настроить повторяемую работу | Форма расписания и условий мониторинга с понятным описанием результата | Меньше ошибок в параметрах автоматизации | После v1, через существующие инструменты |
| Использовать мини-инструмент | Калькулятор оценки, редактор параметров, проверка конфигурации | Мгновенная обратная связь на изменение значений | После v1, ограниченные локальные функции |

Три демонстрации для первой версии: «собери бриф задачи», «сравни подходы и дай выбрать», «покажи параметры следующего шага и дай их поправить». Они используют один общий набор компонентов.

Проверка параметров в A2UI означает передачу пользовательского выбора агенту. Разрешения на запуск инструментов остаются в существующем механизме approvals.

## Представление в клиентах

| Клиент | Представление | Взаимодействие |
| --- | --- | --- |
| Dashboard | Прокручиваемый блок над компоузером, текстовый fallback остаётся в ленте | Мышь и клавиатура; существующий кастомный dropdown |
| ClientNative, macOS | Нативный SwiftUI-блок с возможностью свернуть форму | Нативные поля, выделение, фокус и доступность |
| ClientNative, iPhone/iPad | Тот же сценарий с адаптивной компоновкой и прокруткой | Touch, системная клавиатура, масштабирование текста |
| TUI | Краткое представление в ленте и отдельная область взаимодействия | Tab/Shift-Tab, стрелки, Enter; Escape возвращает в чат с сохранением черновика |

Для v1 TUI поддерживает все действия общего каталога. Широкое сравнение превращается в последовательность подписанных блоков. Позже графики получают табличное представление с теми же исходными данными.

Расширенная панель — способ открыть тот же интерфейс, а не отдельная копия состояния. Пользовательский текст, вложения и черновик компоузера сохраняются при работе с формой.

Оформление принадлежит клиенту и следует `docs/dashboard-style.md`, включая отдельную нейтральную desktop-палитру. Агент задаёт содержание и смысловую структуру, клиент — шрифты, цвета, интервалы и адаптацию.

## Основа реализации

В текущем Sloppy уже есть структурированные события сессии, запросы ввода, approvals, встроенные скиллы и HTML-виджеты рабочих пространств. Отдельной реализации A2UI в проверенных Sources, Dashboard/src и ClientNative/Sources не обнаружено. Существующие вопросы и approvals сохраняют свои контракты; A2UI использует общую доставку и механизм продолжения сессии.

Базовый протокол — [A2UI v0.9.1](https://a2ui.org/specification/v0.9.1-a2ui/), с зафиксированной схемой и собственным версионированным каталогом Sloppy. На дату исследования upstream обозначает v0.9.1 как production, v1.0 — candidate. Каталог Sloppy объявляет только реально реализованные компоненты; полная поддержка Basic Catalog не обещается.

Первый каталог: Text, Column, Row, TextField, CheckBox, ChoicePicker, Button. Текстовое поле поддерживает текстовое и числовое значение с проверкой типа; обязательность и границы задаются декларативно. Сравнение в v1 собирается из этих примитивов. Таблицы, даты, графики, медиа и произвольные вычисления добавляются отдельно.

Поток данных: **агент → ui.render → проверка Core → сохранённое событие → renderer клиента → пользовательское действие → Core → исходная сессия агента**.

- Общие модели и применение A2UI-обновлений вынести в небольшой внутренний SwiftPM-пакет без UI-зависимостей, доступный Core, ClientNative и TUI. Dashboard реализует тот же контракт; общие JSON-примеры проверяют эквивалентность.
- Новые инструменты: `ui.catalog` возвращает версию, возможности и схемы; `ui.render` принимает пакет стандартных A2UI-сообщений create/update/delete и обязательное текстовое представление. Инструменты привязаны к текущей сессии; агент не выбирает произвольного получателя.
- `ui.render` возвращает идентификатор и ревизию поверхности либо структурированную ошибку с местом нарушения схемы. Невалидное обновление сохраняет предыдущую рабочую версию. Публикация сама по себе не приостанавливает агента; скилл завершает текущий ответ, если дальше требуется пользовательский ввод.
- Snapshot и обновления доставляются существующим каналом событий сессии. Новый UI-payload — необязательные данные при известном типе события и текстовом fallback. Не добавлять необъявленные значения в существующие enum: старый Swift-клиент должен продолжить декодировать историю.
- Ответ формы отправляется через новый session-scoped endpoint `POST /v1/agents/{agentId}/sessions/{sessionId}/ui-surfaces/{surfaceId}/actions`. Запрос содержит идентификатор действия, ревизию поверхности и выбранные значения; Core проверяет принадлежность сессии, схему и повторную доставку.
- Сервер хранит опубликованную поверхность и принятые ответы. Незавершённый ввод — локальный черновик клиента; после явной отправки результат виден на остальных устройствах. Синхронное совместное редактирование черновика не входит в v1.
- В v1 кнопки передают данные агенту; изменение полей и раскрытие содержимого работают локально. Вызовы инструментов после ответа проходят обычную политику разрешений. Прямые действия из UI появятся отдельным расширением каталога.
- Состояния: готово, отправляется, принято, устарело, ошибка, прервано. Повторный запрос с тем же идентификатором действия не запускает второй ход агента. При конфликте между устройствами сервер отклоняет устаревший ответ и возвращает актуальное состояние.
- История после перезапуска восстанавливает представление, но не повторяет действия. Обновления модели данных не затирают несохранённый локальный ввод без явного разрешения конфликта. При отсутствии сети можно редактировать черновик; отправка требует подключения.

В A2UI v1 не исполняются HTML, JavaScript, shell-команды или произвольные сетевые запросы из описания интерфейса. Существующие HTML-артефакты и workspace widgets остаются вариантом для полноценных мини-приложений. Это разные форматы доставки результата.

## Встроенный скилл агента

Предлагаемое имя — **`sloppy/a2ui`**, команда — `/a2ui`. Это скилл для агента внутри Sloppy. Его включение входит в последний этап v1, когда инструменты и renderer уже работают.

Будущий каталог: `Sources/sloppy/Resources/Skills/a2ui/`. Состав: `SKILL.md`, краткое описание протокола, JSON-примеры трёх демонстраций и заметка о поведении TUI. Зарегистрировать как first-party skill в `BuiltInSkillCatalog`; обеспечить выдачу новым и существующим агентам без перезаписи пользовательских правок.

Содержимое скилла:

1. Определить, помогает ли интерфейс выполнить текущую задачу. Использовать текст для простого ответа и существующий запрос ввода для одного обычного уточнения.
2. Получить каталог через `ui.catalog`, использовать только объявленные компоненты, действия и версии. Полную схему не помещать в каждый bootstrap: краткое описание находится в каталоге скиллов, инструкции и примеры читаются по необходимости.
3. Создать минимальную форму или сравнение с понятными подписями, редактируемыми значениями и одной основной кнопкой. Рекомендованный вариант помечается текстом; он не отправляется автоматически.
4. Передать описание через `ui.render`, исправить структурированные ошибки проверки. Использовать стабильные идентификаторы при обновлениях одной поверхности.
5. Кратко объяснить назначение интерфейса и оставить текстовый способ ответа. Если нужен ввод, закончить текущий ход без повторных напоминаний.
6. Продолжать задачу по подтверждённому структурированному действию из этой сессии. Подписи кнопок и свободный текст модели не становятся эвристиками управления.
7. Использовать существующие источники и инструменты для получения фактов. Не подставлять вымышленные результаты и не изображать успешное выполнение операции одной сменой UI-состояния.

Триггеры: пользователь просит форму, интерактивный выбор, сравнение с последующим действием или интерфейс для настройки параметров; агент видит пользу от нескольких связанных полей. Скилл не подменяет создание сайта, изменение самого приложения и разрешение на внешние действия.

Скилл и каталог поставляются вместе. В чате без поддержки A2UI агент использует обычный текст/существующие вопросы. Для ACP сначала поддерживается native Sloppy-runtime; приём A2UI от внешних ACP-агентов — отдельная последующая интеграция.

## Приёмка и следующие этапы

v1 готова, когда все три демонстрации проходят на Dashboard, macOS, iOS и TUI: создание интерфейса, изменение значений, отправка и продолжение исходной сессии. Для неинтерактивного или устаревшего клиента доступен текстовый ответ.

Обязательные проверки: несовместимая версия/каталог; неправильный JSON и тип значения; неизвестный компонент; ошибочные ссылки и циклы; ограничение размера/глубины; повторная отправка; два устройства; восстановление после сбоя; чужая сессия; сохранение компоузера; прерванная генерация; недоступный агент; клавиатура и доступность. Восстановление истории не запускает побочные эффекты. Проверить отсутствие автоматической отправки из-за существующего `autoApproveInput`.

Для скилла проверить три положительных сценария и три отрицательных: простой ответ, обычное уточнение и создание сайта. Оценивать реально опубликованный валидный интерфейс и правильное продолжение сессии, а не наличие определённых слов в ответе.

Проверки реализации идут от узких тестов к соответствующим CI-командам. Нативный клиент проверить запуском на macOS и iOS Simulator; успешную сборку и реальное взаимодействие с агентом фиксировать отдельно. Для Dashboard — typecheck, production build и браузерный сценарий; для TUI — клавиатурный сценарий в терминале.

Критерий продуктовой пользы: пользователь проходит бриф/выбор с меньшим числом сообщений, может проверить отправленные значения и получает продолжение именно по ним. Сравнить с текстовым сценарием на одинаковых задачах; отдельно учитывать ошибки рендеринга, отклонённые ответы и повторные попытки, без записи значений полей в диагностику.

После проверки v1: таблицы с выбором строк и локальными фильтрами → отчёты с графиками и источниками → ограниченные локальные вычисления и разрешённые прямые действия → закрепление и переиспользование интерфейсов в workspace. Эти возможности требуют отдельной спецификации перед реализацией.

Порядок небольших PR описан в [карте поставки](../tbd/decompositions/2026-10-27-a2ui-clients.md).


## Первый Core/API-срез (история реализации)

Общий пакет `Packages/SloppyA2UI` не зависит от SwiftUI, терминала или внешних библиотек. Он описывает материализованный snapshot с `protocolVersion`, `catalogId`, `surfaceId`, `revision`, `fallbackText` и `components`. Это внутреннее представление состояния; оно не подменяет стандартные A2UI transport envelopes, которые добавляются на этапе публикации.

Начальный поддерживаемый набор — literal Text и Column; точка входа — компонент `root`. Проверяются уникальность идентификаторов, ссылки, циклы, повторное использование узла и достижимость всех компонентов. Пределы: 128 компонентов, глубина 16, 128 UTF-8 байт на идентификатор, 16 KiB на текст и fallback, 64 KiB на JSON snapshot. Версия протокола — `0.9.1`, каталог — `urn:sloppy:a2ui:catalog:v1`.

Snapshot сохраняется в необязательном `message.uiSurface` существующего события `message`. Обычные текстовые сегменты остаются представлением для старого клиента. Неизвестный/повреждённый UI-payload не мешает декодированию текста. Новых значений в существующих wire enum нет; миграция SQLite не нужна.

`GET /v1/agents/{agentId}/sessions/{sessionId}/ui-surfaces` возвращает JSON-массив последних поддерживаемых валидных snapshot по `surfaceId`, отсортированный по идентификатору. Источник — журнал этой сессии; учитываются только assistant-message события с совпадающими agent/session. Некорректная или устаревшая ревизия не вытесняет ранее сохранённую рабочую. Для пустой сессии возвращается `[]`, неизвестного агента/сессии — 404, неправильного ID — 400. Маршрут использует существующую авторизацию Core.

На этом этапе нет renderer, действий формы или доступного агенту `ui.render`. Данные можно прочитать из журнала; восстановление и GET ничего не выполняют. Следующий срез добавляет публикацию и применение стандартных A2UI-обновлений.


## Публикация UI — текущий контракт

`ui.catalog(surfaceId?)` читает каталог только текущей сессии. Он возвращает схемы Text/Column/Row/TextField/CheckBox/ChoicePicker/Button, список операций и до 32 записей с revision/isDeleted. По конкретному surfaceId возвращается полный snapshot, включая tombstone. Это позволяет продолжить редактирование после перезапуска, не загружая все данные UI в контекст при каждом чтении каталога.

`ui.render(messages, expectedRevision, fallbackText)` принимает messages как JSON-encoded array string — тот же подход к сложному JSON, который уже используется конфигурационными tools Sloppy. Массив содержит 1–32 стандартных A2UI-конверта с `version: "v0.9.1"`, не более 64 KiB и ровно одну surface на пакет. Поддерживаются createSurface, updateComponents, updateDataModel, deleteSurface. Пакет сначала целиком применяется к копии состояния и проверяется; только затем одним обычным message-событием сохраняется snapshot и публикуется в текущий поток. Промежуточное дерево без root не публикуется.

expectedRevision обязателен: 0 для ещё не созданной surface, актуальный номер из каталога для остальных. Удаление хранится как snapshot-tombstone с новой ревизией. GET ui-surfaces скрывает tombstone, а каталог позволяет узнать его ревизию для повторного создания ID. Версия после повторного создания продолжает расти; восстановление журнала не возвращает удалённую surface.

updateComponents добавляет или заменяет компоненты по ID. Начальный каталог требует полностью связное дерево: для исключения старых узлов используется атомарный delete/create с новым набором компонентов. updateDataModel сохраняет типы JSON, различает null и отсутствие value, поддерживает JSON Pointer с экранированием и замену/удаление существующих array-индексов. Отсутствующие object-поля можно создать; удаление отсутствующего поля ничего не создаёт. Привязки полей — абсолютные непересекающиеся JSON Pointer; функции не поддерживаются.

После успеха tool возвращает только surfaceId/revision/isDeleted. Ошибки схемы содержат код invalid_ui_payload и path; конфликт — ui_revision_conflict и currentRevision. Отклонённый пакет не меняет журнал и не отправляет UI-событие. Публикация не исполняет инструменты и не приостанавливает ход агента. UI-tools зарегистрированы в общем каталоге; вызовы разрешены только если последнее пользовательское сообщение явно объявляет `supportsA2UI: true`. Без объявления клиент получает обычный текст или planning.request_input.


## Завершённый v1

`POST /v1/agents/{agentId}/sessions/{sessionId}/ui-surfaces/{surfaceId}/actions` принимает UUID actionId, revision, componentId кнопки и полный словарь значений по binding. Сервер проверяет схему, типы, required/range/options, актуальную ревизию и владельца long chat. Принятый ответ атомарно сохраняется в существующей долговечной очереди сообщений вместе со snapshot, затем отражается в журнале и продолжает ту же сессию. Повтор с тем же UUID и содержимым возвращает тот же receipt, конфликт получает 409. Восстановление checkpoint не отправляет ответ повторно.

Клиенты хранят черновик отдельно от компоузера и изолируют его по серверу/агенту/сессии/surface. Изменённые значения сохраняются при обновлении серверных defaults; подтверждённые/удалённые формы закрываются. При неопределённом сетевом результате повтор использует прежний UUID. В TUI форма открывается Ctrl+Y или `/ui`, переключается Ctrl+N/P, Escape возвращает в чат.

Скилл `sloppy/a2ui` доступен как `/a2ui` и через семантический autoRoute. Полный каталог загружается по запросу; краткий tool receipt не раздувает контекст. Три общих примера лежат в `Packages/SloppyA2UI/Tests/SloppyA2UITests/Fixtures` и в references скилла: brief, comparison, parameters. Это Sloppy-каталог A2UI v0.9.1; произвольные Basic Catalog-компоненты, HTML, локальный код и прямое исполнение инструментов в v1 не принимаются.
