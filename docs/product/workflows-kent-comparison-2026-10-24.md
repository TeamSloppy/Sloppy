# Sloppy workflows: сравнение с Kent

Дата: 24 октября 2026. Проверенная версия Sloppy: рабочая копия от `41384ce5`; изменения интерфейса описаны отдельно ниже.

> Обновление после первого этапа: в ветке `codex/workflow-agent-execution` агентские шаги запускают настоящие новые сессии и проверяют typed terminal outcome. Убраны успех без исполнителя, молчаливое завершение без перехода и ряд неисполняемых блоков. Исследование ниже описывает исходное состояние на `41384ce5`; восстановление состояния, версии, контракты и параллельность остаются следующими этапами. Карта этапов: `docs/tbd/decompositions/2026-10-24-workflow-runtime.md`.

## Вывод

В Sloppy уже есть настоящий фундамент workflow: определения графов, API, инструмент для агента, редактор, история запусков, выполнение зарегистрированных инструментов и ожидание решения человека. Однако исполнитель пока соответствует раннему последовательному MVP. Часть блоков в палитре описывает поведение, которого в runtime ещё нет.

Главный разрыв — соответствие нарисованного процесса фактическому выполнению. Сначала нужно устранить ложный успех и восстановление с потерей состояния; затем добавлять более сложную оркестрацию.

Метод: полностью прочитана документация [Kent Workflows](https://kent.sh/workflows/) и связанные страницы [Configuration](https://kent.sh/config/), [Worktrees](https://kent.sh/worktrees/), [Headless](https://kent.sh/headless/), [Server](https://kent.sh/server/). Возможности Kent ниже — заявления его документации, а не результат запуска его приложения. Sloppy проверен по текущим исходникам и существующим тестам. UI проверен отдельно на изолированных тестовых данных; эти данные не доказывают выполнение параллельного процесса.

## Сопоставление

| Область | Kent по документации | Sloppy по текущему коду | Практическое следствие |
| --- | --- | --- | --- |
| Визуальный граф | Редактор, инспектор перехода | Граф, палитра, позиции, конфигурация, связи уже есть | Это развитие существующего продукта, а не создание с нуля |
| Создание агентом | Генерация workflow агентом | `project.workflow`: propose, start, link_agent_step, list, status | Здесь у нас уже есть сопоставимая точка входа |
| Агентский шаг | Роль и сессия | `agent` и `ai_transform` не обрабатываются диспетчером workflow-инструментов | Успешный шаг ещё не означает работу модели |
| Переход | Ключ, критерий, ветви, параметры | Ребро хранит source/target, conditionKey и сокеты | Нет полноценного контракта передачи работы |
| Параллельность | Fan-out и join | Исполнитель выбирает один следующий node ID | Несколько исходящих линий не запускают несколько веток |
| Контекст | New, continue, compact; выбор источника | Нет политики сессии на переходе | Нельзя настроить независимое ревью и возвращение к прежнему исполнителю |
| Результат модели | Structured/tool/shell completion | Нет workflow-контракта завершения агентского шага | Нельзя надёжно выбрать следующий этап по подтверждённому результату агента |
| Человек | Подтверждение перехода, вопросы | Отдельные human-узлы и persisted pending actions | Основа есть, но UI Human Input предлагает те же три решения |
| Скрипты | JSON stdin/stdout, проверка результата | Bash, JS/Python, tool, HTTP, sub-workflow через tool bridge | Инструменты реально вызываются; строгого контракта результата перехода нет |
| Задачи | Этапы становятся колонками доски | taskId опционален, статус меняется отдельным Update Task; ручной Run передаёт служебное сообщение | Переход графа и жизненный цикл задачи ещё не составляют единый процесс |
| Изоляция | Политика worktree на workflow | Workflow-модели не задают такую политику | Изоляция исполнения не является гарантией самого workflow |
| Ограничения | Concurrency, invalid-completion budget | Жёсткие 25 посещений узла внутри одного walk | Настройка maxIterations в палитре не управляет этим лимитом |

## Что конкретно недоделано в Sloppy

### 1. У Agent есть конфигурация, но нет исполнения

`CoreService.workflowToolInvocationRequest` распознаёт bash, code, web_request, tool и sub_workflow. Ветка по умолчанию возвращает nil; `agent` и `ai_transform` отдельных обработчиков не имеют. Затем `WorkflowRunner.walk` при nil-результате переносит config в output и добавляет status=succeeded.

Выбор agentId, model и prompt в редакторе сам по себе не создаёт сессию, не ждёт работу модели и не проверяет результат. Это наиболее опасная недостающая возможность: внешне workflow завершён успешно, но ожидаемая работа могла не начаться.

Существующий тест `workflowRunnerRecordsAgentAndToolStepsAsWorkflowActions` прямо ожидает succeeded без injected executor. Поэтому зелёные текущие тесты не доказывают агентскую оркестрацию.

Источники: `Sources/sloppy/CoreService+Workflows.swift`, `workflowToolInvocationRequest`; `Sources/sloppy/Workflows/WorkflowRunner.swift`, `walk`; `Tests/sloppyTests/WorkflowRunnerTests.swift`.

### 2. Fan-out и барьер объединения отсутствуют

`nextNodeID` возвращает первый совпавший условный переход либо первое ребро без условия. `currentNodeIds` — массив в wire model, но runner записывает в него один ID. Отдельного исполнительного типа join нет; палитра Merge создаёт обычный condition.

Граф Implementation → Review и QA можно сохранить и показать, но runner не начнёт обе ветви и не дождётся двух результатов. Рамка команды в обновлённом интерфейсе обозначает принадлежность узлов команде; она не меняет исполнительную семантику.

### 3. Expression и Loop не вычисляют выражения

Ветка condition объединяет исходный context.input с config. Она не вычисляет строку expression. Сопоставление рёбер работает по явному bool(true) либо строковым полям conditionKey, decision, status, result. Это полезный детерминированный механизм, но он не реализует обещанный редактором язык выражений.

Если следующего подходящего ребра нет, walk завершает run как completed. Это позволяет незавершённому графу выглядеть законченным. Ограничение 25 посещений существует, но config.maxIterations не используется, а счётчик создаётся заново при каждом walk.

### 4. После human approval теряется контекст предыдущих этапов

`resume` создаёт новый Context с input=output решения человека. `walk` заново создаёт пустой nodeOutputs. Накопленные `nodes.<id>.output` и исходный input не восстанавливаются из сохранённых шагов.

Пример: подготовлен путь approved_plan, процесс остановлен на подтверждении, следующий скрипт ссылается на output планирования. После resume прежний набор выходов в scoped input отсутствует. Неразрешённый placeholder resolver оставляет в исходном виде, а не превращает в понятную ошибку контракта.

Нужен persisted checkpoint: исходный input, результаты этапов, сессии, счётчики и активные ветви.

### 5. Номер версии записан, snapshot графа не закреплён

WorkflowRun хранит workflowVersion. Однако file store обновляет тот же JSON-файл, повышая version. При разрешении human action сервис загружает текущее определение по workflowId и передаёт его в resume.

Если изменить граф, пока run ждёт человека, продолжение интерпретирует уже изменённые узлы и рёбра. Это нарушает ожидаемое значение сохранённого номера версии. Нужен immutable snapshot определения для каждого запуска либо хранилище исторических версий.

Источники: `Sources/sloppy/Stores/WorkflowDefinitionFileStore.swift`, `update`/`write`; `Sources/sloppy/CoreService+Workflows.swift`, `resolveWorkflowPendingAction`.

### 6. Валидация в основном структурная

Проверяются стартовая вершина, идентификаторы, ссылки на lanes/nodes, имена и координаты. Не проверяются наличие исполнимого обработчика, обязательный агент, достижимость конца, полнота условий, допустимость циклов и наличие данных на всех путях к шаблону.

Полезное улучшение — проверять граф до Save/Run и показывать ошибки возле конкретного узла или перехода. Важнее запретить заведомо неисполнимый запуск, чем рисовать дополнительные типы блоков.

### 7. Некоторые другие блоки также имеют только поверхностную семантику

Notify/Channel и Project Task в runner сейчас переносят config в output. Это не отправка сообщения в канал и не загрузка полной задачи. Human Input и Human Approval создают однотипное pending action с approved/rejected/changes_requested; в UI отсутствует ввод свободного ответа.

Code предлагает больше языков, чем поддерживает диспетчер: Python запускается python3, остальные значения интерпретируются как Node.js. Не следует считать наличие Swift/TypeScript/Bash в таком переключателе доказательством их поддержки этим блоком.

Скорость, стоимость, расход токенов и надёжность Kent экспериментально не сравнивались. Настройки контекста дают инструменты управления расходом, но не доказывают экономию на нашей нагрузке.

## Что уже ценно и можно сохранить

- Файловые определения workflow и отдельная история запусков/шагов/действий.
- API и агентский инструмент создания и запуска графов.
- Реальные вызовы инструментов через существующий tool execution layer.
- Работающие остановка на human action, разрешение решения и продолжение простого процесса.
- Связь с проектом и taskId, изменение статуса задачи.
- Детерминированное ветвление по явным протокольным значениям.
- Работающий редактор, drag-and-drop узлов, создание связей и редактирование конфигурации.

Это позволяет развивать workflow внутри существующей архитектуры. Переписывание всего runtime или перенос кода конкурента не требуется.

## Предлагаемый порядок развития

1. **Устранить ложный успех.** Неподдерживаемый или неправильно настроенный блок должен останавливаться с объяснением. Завершение без допустимого перехода не должно автоматически означать успех. Добавить настоящий agent executor через существующие сессии, с явным завершением и ошибками.
2. **Сделать продолжение воспроизводимым.** Закрепить snapshot графа, сохранять checkpoint и восстанавливать outputs, input, session bindings и бюджеты попыток. Покрыть ожидание человека и изменение definition во время паузы.
3. **Ввести контракты переходов и управление контекстом.** Обязательные outputs, их валидация и адресация; явный выбор fresh/continue/compact. Переносить существующую конфигурацию совместимо, а не ломать сохранённые workflow.
4. **Добавить параллельное исполнение.** Модель активных ветвей, fan-out, join с определённым правилом ожидания, агрегация outputs, отмена и ошибки ветвей. После этого сценарий Review + QA станет реальным.
5. **Привязать окружение и задачи.** Политика worktree и setup, recovery/retry, удобный запуск с фактическим входом из задачи, своевременное обновление статусов и ожиданий в интерфейсе.

Критерий первой полноценной версии: задача проходит подготовку → выполнение агентом → проверку → решение человека → продолжение, переживает изменение открытого редактора и сохраняет все необходимые артефакты и данные. Параллельность следует проверять отдельно фактическим запуском двух ветвей и барьером объединения.

## Что изменено в интерфейсе сейчас

В существующем Dashboard-редакторе сохранены wire format и исполнительная семантика, а представление переработано:

- Большое нейтральное тёмное полотно с точечной сеткой, которая движется и масштабируется вместе с графом.
- Компактная вертикальная панель добавления, настроек, fit, zoom и масштаба 100%.
- Выбор workflow, палитра, настройки и журнал открываются по запросу.
- Скруглённые карточки с названием, типом и ответственным; рамки существующих team lanes.
- Скруглённые ортогональные связи, стрелки и кликабельные подписи непосредственно на маршруте.
- Обратные переходы проходят над графом; анимация связей используется только для активных исходных узлов и отключается при Reduce Motion.
- Разворачивание редактора, закрытие панелей через Escape, клавиатурное открытие настроек узла, увеличенная область захвата портов.

Это изменение интерфейса. Оно не добавляет отсутствующие гарантии исполнения, перечисленные в исследовании.
