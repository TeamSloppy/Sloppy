# Вывод команд, изменения и восстановление чата

- Дата — 2026-11-20.
- Целевые клиенты — TUI, Dashboard и Client Native.
- Ветка интеграции — `main`.
- Бюджет — до 600 строк для ревью на срез. Оценки уточняются по фактическому diff.
- Статус — утверждена. Срезы 1–6 реализованы и проверены локально. Срезы 7–8 запланированы.

## Границы и проверка

### 1. Вывод команды из Core в TUI

- Привязать вывод к существующему ID вызова. В активном потоке передавать ограниченный по размеру снимок хвоста с ревизией, чтобы пропуск промежуточного обновления или переподключение не ломали отображение.
- Финальный статус, код возврата и ссылки на полный stdout и stderr брать из сохранённого результата инструмента. Использовать действующий доступ к артефактам сессии.
- Расширить известный тип сообщения необязательными данными либо передавать обновления только подписчикам, которые объявили поддержку. Проверить старый декодер и чтение старой истории.
- Сквозной сценарий TUI — две команды выводят строки вперемешку, одна падает. Каждая строка остаётся у своей команды. Проверить раскрытие полного лога, переподключение и завершение при ошибке.

### 2–3. Вывод в Dashboard и Client Native

- Использовать тот же ID вызова и порядок ревизий. Поддержать раскрытие отдельной команды и полный лог из существующего интерфейса артефактов.
- Проверить восстановление после переключения чата, длинный вывод и отсутствие скачка прокрутки во время чтения истории. В Client Native проверить нативное раскрытие и состояние после обновления на macOS и iOS.

### 4–5. Diff за ход

- Брать фактические состояния файла до и после успешной записи в существующей точке мутации. Собирать итоговый diff по ходу и рабочей копии. Передать один и тот же сохранённый результат в три клиента.
- При несовпадении хешей между последовательными записями явно обозначить неполную атрибуцию файла. Проверить сценарий, в котором пользователь меняет файл между двумя операциями агента. Отдельно проверить отменяющие друг друга правки, разные рабочие копии и перезагрузку истории.
- Для файловых операций через shell оставить существующий diff рабочего дерева. Связь с ходом показывать там, где Core знает источник изменения.

### 6. Восстановление через Core

- Возобновлять конкретный прерванный ход по сохранённым событиям внутри той же сессии. `/restore` вызывает операцию Core. Дополнительное указание из команды передаётся отдельным полем.
- Проверить владельца сессии, активный ход, ожидающий ввод и незакрытые approvals. Сохранить действующий механизм сверки вызовов с неизвестным эффектом.
- Проверить перезапуск Core между вызовом и результатом инструмента, повторный запрос восстановления и доставку позднего результата. Продолжение должно запускаться один раз и сохранять подтверждённый прогресс.
- Выполнено для нативных чатов. TUI по `/restore [указание]` передаёт Core ID исходного сообщения и ID прерванной попытки. Повтор операции с этими ID использует сохранённую запись о восстановлении. Профильный прогон из 33 тестов проверил восстановление после перезапуска, отсутствие нового сообщения, сохранение черновика, повтор запроса и обработку позднего результата.

### 7–8. Фоновое сжатие

- Измерить длительность самой суммаризации, её долю в задержке перед запросом к модели и частоту срабатывания на длинной истории с инструментами.
- При подтверждённой задержке строить checkpoint на стабильном префиксе и применять его только при совпадении префикса и конфигурации модели. Новые события в хвосте, последнее уточнение и незавершённая пара «вызов — результат» должны пережить установку checkpoint.
- Сравнить p50 и p95 с исходным прогоном на том же сценарии. Сохранить синхронное сжатие как рабочий путь при достижении предельного размера контекста.

## Проверки и рабочая копия

В каждом срезе Core сначала проверяется узкими Swift-тестами. Для Dashboard запускаются typecheck, production build и живой сценарий в браузере. Для Client Native используются профильные тесты и живые сценарии на целевых платформах.

Изменения предыдущего цикла работы уже есть в текущей рабочей копии. Начинать реализацию следует в отдельной рабочей копии, сохранив эти изменения. Публикация PR и развёртывание в эту карту не входят.

## Решения

- 2026-11-20 — обе функции ленты должны работать в TUI, Dashboard и Client Native. Общий контракт и первый потребитель поставляются вместе. Остальные клиенты могут подключаться независимо.
- 2026-11-20 — фоновое сжатие зависит от замера, поскольку текущий Core уже сохраняет checkpoint с ID событий исходного префикса.
- 2026-11-20 — срез 1 отправляет `command_output` только по подписке `commandOutput=1` на SSE или WebSocket. Старый Dashboard перечитывает сессию на heartbeat, поэтому вывод команды получил отдельное событие. В TUI команда `/logs` читает сохранённые stdout и stderr по страницам. Прогон после добавления подписки — 253 теста, release-сборки `sloppy` и `SloppyNode` успешны. Полный изолированный прогон до изменения подписки — 2 797 тестов.
- 2026-11-20 — Dashboard и основной чат Client Native используют общий поток и постраничное чтение логов. Ветки — `codex/chat-command-output-dashboard` и `codex/chat-command-output-native`. Dashboard прошёл typecheck, production build и браузерную проверку двух команд, переподключения и чтения лога. Client Native собрался для macOS и iPhone Simulator, два профильных теста прошли. Проверки Core подтвердили привязку вывода к вызову, отсутствие пропусков курсора у обычных подписчиков и права чтения лога в Console.
- 2026-11-21 — срезы 4–5 подключены сразу в TUI, Dashboard и Client Native. Core сохраняет diff успешных `files.edit` и `files.write` в итоговом событии хода. Файлы с несовпадающими хешами между записями получают пометку о смешанных изменениях. Прошли профильные тесты Core и TUI, тесты файловых операций и Undo, браузерная проверка и сборка Dashboard, тесты Client Native на macOS и сборка для iPhone Simulator.
