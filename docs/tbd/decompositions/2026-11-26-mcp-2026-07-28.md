# Поддержка MCP 2026-07-28 в Sloppy

- Дата — 2026-11-26.
- Статус — согласовано 2026-11-26. Этапы объединены в один PR.
- Ветка интеграции — `main`.
- По решению владельца все этапы входят в один PR.
- Исходные документы — [анонс Anthropic](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more) и [changelog MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

## Цель

Sloppy как MCP-клиент подключается к серверам с ревизией `2026-07-28` по HTTP и stdio, продолжает работать с ранее поддержанными серверами и использует Skills, Tasks и Elicitation в агентских сессиях. Первый пользовательский результат — обычный MCP-инструмент нового сервера доступен через существующие агентские инструменты и динамический каталог.

File Uploads, MCP Apps и Enterprise Managed Auth требуют отдельных продуктовых решений. Tool search из статьи относится к выдаче инструментов модели и не участвует в согласовании версии MCP. Экспорт возможностей Sloppy в виде MCP-сервера и ACP-мосты остаются за границами этой карты. [Анонс Anthropic](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more), [экспериментальная спецификация File Uploads](https://github.com/modelcontextprotocol/experimental-ext-file-uploads).

## Текущее состояние

- `MCPServerConnection` создаёт SDK `Client` и вызывает `connect`. `MCPClientRegistry` обслуживает явный `mcp.call_tool`, динамические инструменты, resources и prompts. Ответ вызова сейчас сводится к `content` и `isError`. [MCPClientRegistry.swift](../../../Sources/sloppy/MCP/MCPClientRegistry.swift), [MCPTools.swift](../../../Sources/sloppy/Tools/AgentTools/MCP/MCPTools.swift).
- `Package.resolved` фиксирует Swift SDK 0.12.1. Windows использует локальную копию 0.12.1 с патчами транспорта. Документация upstream указывает поддержку `2025-11-25`. У vendored HTTP-транспорта есть ограничение SSE на Linux и Windows. [Package.resolved](../../../Package.resolved), [Vendor/swift-sdk/UPSTREAM.md](../../../Vendor/swift-sdk/UPSTREAM.md), [Swift SDK](https://github.com/modelcontextprotocol/swift-sdk).
- Агентские skills сегодня загружаются через файловый каталог. MCP-источник должен сообщать свои метаданные отдельно и загружать инструкции по запросу. [AgentSkillsFileStore.swift](../../../Sources/sloppy/Agent/AgentSkillsFileStore.swift), [AgentSessionOrchestrator.swift](../../../Sources/sloppy/Agent/AgentSessionOrchestrator.swift).

### 1–3. Базовая совместимость

- На первом этапе проверить доступную upstream-версию Swift SDK и Windows-сборку на живых legacy и stateless fixtures. Если upstream уже покрывает обе версии и платформы, использовать его. По текущим данным предпочтителен небольшой Swift-адаптер за `MCPServerConnection`: SDK и subprocess остаются рабочими для прежнего протокола, а новая ветка использует общий для HTTP и stdio код JSON-RPC и metadata. Первый этап даёт наблюдаемый результат через диагностику сервера. Путь вызова нового сервера подключается на втором этапе.
- В качестве альтернативы можно дописать stateless поддержку в Swift SDK и поставлять её на всех платформах через один upstream или fork. Это уменьшит объём протокольного кода в Sloppy, но добавит работу с API SDK, релизами зависимости и Windows-патчами. Решение принять после проверки обеих версий на HTTP и stdio.
- Для HTTP передавать обязательные поля `_meta` и заголовки маршрутизации из спецификации. Проверять JSON-RPC тело ошибок при выборе версии. Ошибки аутентификации, сети и распознанные ошибки нового протокола имеют отдельную диагностику. Для stdio обработать probe timeout, несовместимую версию, закрытие процесса и корректный переход к `initialize`. Переигрывать только операции согласования и запросы, отклонённые на уровне версии до выполнения. [Версии](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), [stdio](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).
- На втором этапе сохранить стабильные ID динамических инструментов, схемы, правила доступа, ошибки и пагинацию. Добавить типизированные варианты результата и передачу `structuredContent`. Для HTTP поддержать заголовки `Mcp-Name` и `Mcp-Param-*` из схем инструментов. Принять JSON и конечный ответ через SSE с лимитами и отменой. Долгоживущие подписки реализуются на этапе 6. Проверить обработку SSE на Linux и Windows.
- Первый профиль подключения использует существующие настроенные HTTP headers. Интерактивное MCP OAuth требует отдельного решения о включении в релиз и собственной проверки защищённого сервера. При включении разбить на обнаружение сервера авторизации и получение токена с PKCE, затем обработку повторной авторизации, scope и хранение учётных данных. [Авторизация MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

### 4–5. Skills over MCP

- После обнаружения `resources` и `io.modelcontextprotocol/skills` загружать метаданные через `skills/list` и `skills/get`. Идентификатор навыка включает ID исходного сервера и URI. В контекст до активации идут имя, описание и идентификатор. Инструкции и разрешённые файлы подгружаются через `resources/read` при использовании навыка.
- Первый релиз поддерживает навыки с манифестом файлов. Хранить использованный манифест, проверять размер, SHA-256 и frontmatter, ограничивать чтение URI манифеста. Разрешение на активацию привязывать к источнику и манифесту. При обновлении файлов получать новое разрешение. Контент проходит действующую политику доступа к инструментам. Кэш остаётся вне путей загрузки локальных skills и изолируется по серверу и контексту авторизации. [Skills extension](https://modelcontextprotocol.io/extensions/skills/overview).
- Сквозная проверка — агент видит два одноимённых навыка с разными источниками, загружает выбранный по запросу, читает файл после проверки, получает новую точку подтверждения после изменения файла.

### 6. Потоки и актуальность каталогов

- Передавать прогресс в существующие события инструментов. Для объявленных сервером событий каталога использовать `subscriptions/listen`, инвалидировать соответствующий кэш и корректно переподключаться. Остановить подписку при отключении сервера или смене учётных данных. Уважать `ttlMs` и `cacheScope` при кэшировании списков. [Changelog MCP](https://modelcontextprotocol.io/specification/2026-07-28/changelog).

### 7–8. Elicitation

- Через multi-round-trip принимать `input_required`, показывать схему формы в чате и отправлять ответ с исходным непрозрачным `requestState`. Различать accept, decline и cancel. Проверять схему и права пользователя. Для URL-режима показывать доверенный контекст запроса и адрес перед открытием браузера. Обрабатывать завершение по предусмотренному спецификацией сценарию.
- Для первого подключения использовать один существующий интерфейс чата. Доступные режимы передавать в capabilities конкретного вызова с учётом интерфейса. Первый интерфейс для форм и внешних ссылок — Dashboard. [Elicitation](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation).

### 9–10. Tasks

- Этап 9 добавляет явный вызов для длительных операций через Core. Типизированно обрабатывать `resultType: task`, сохранять handle вместе с сервером, контекстом доступа и исходным вызовом. Учитывать предложенный интервал опроса и TTL, возобновлять polling после рестарта на том же сервере, поддерживать кооперативный `tasks/cancel`. Объявлять capability только там, где результат можно обработать.
- Этап 10 подключает явный `mcp.call_tool` и динамические инструменты. Агент получает структурированный handle и может продолжить ход. Терминальный результат возвращается в ту же сессию через сохраняемое событие с защитой от повторной доставки. При `input_required` использовать Elicitation из этапов 7–8 и передавать ответ через `tasks/update`. При неизвестном результате исходного вызова после обрыва использовать состояние восстановления Sloppy, сохраняя различие между потерей ответа и подтверждённым созданием задачи. [Tasks extension](https://modelcontextprotocol.io/extensions/tasks/overview).

## Приёмка

- Локальные fixtures для legacy-only, modern-only и dual-era сервера по HTTP и stdio. Проверить два пути вызова инструмента, ресурсы и промпты, параллельные запросы, пагинацию и неизменность ID и настроек существующих интеграций.
- HTTP отдельно проверяет JSON, SSE, ошибки версий и заголовков, отказ доступа и отмену. Матрица включает платформы Core — macOS, Linux и Windows. У каждого заявленного расширения есть позитивный сценарий и случай отсутствия capability.
- Сквозной сценарий — агент читает remote skill, вызывает долгий инструмент по его инструкции, после рестарта Sloppy получает результат в исходной сессии. В отдельных сценариях пользователь отвечает на форму или отменяет действие. Повторный результат не добавляет второе событие.
- Для объединённого PR сначала профильные Swift-тесты, затем подходящие проверки CI. Для итоговой матрицы использовать [MCP Conformance](https://github.com/modelcontextprotocol/conformance) и явно перечислить проверенный профиль, настройки авторизации и поддержанные расширения.

## Решения

- 2026-11-26 — согласована последовательность этапов. Начинаем со Streamable HTTP, затем добавляем stdio и выпускаем Skills первым расширением. Выбор между обновлением Swift SDK и адаптером зависит от проверки upstream на первом этапе. Legacy-путь входит в матрицу совместимости.
- 2026-11-26 — за основу первого релиза принята существующая авторизация через HTTP-заголовки. Интерактивный OAuth, File Uploads, MCP Apps и Enterprise Managed Auth требуют отдельного решения о включении.
- 2026-11-26 — последний релиз Swift SDK совпадает с версией Sloppy (0.12.1), его клиент выполняет `initialize`. Для первого среза выбран HTTP-адаптер в Core. Успешный discovery нового сервера сообщает версию и возможности. [Релиз Swift SDK](https://github.com/modelcontextprotocol/swift-sdk/releases/tag/0.12.1).
- 2026-11-26 — на macOS прошли проверки MCP по JSON и SSE, переход на legacy и повторное согласование после смены credentials. Расширенный набор MCP, HTTP-сервера и роутера прошёл 192 теста. Релизные сборки `sloppy` и `SloppyNode` прошли. Полный прогон завершился по тайм-ауту после ошибок в других наборах. Локальные проверки выполнены на macOS.
