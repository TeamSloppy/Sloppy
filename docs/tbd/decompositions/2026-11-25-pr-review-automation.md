# Автоматизация ревью PR в Sloppy

- Дата — 2026-11-25.
- Репозитории — `Sloppy` и `SloppyPlugins`, ветка интеграции `main` в обоих.
- Статус — реализация в локальных рабочих копиях. Оценки включают код и тесты, цель — до 600 строк на PR.

## Что должно работать

1. На чужом PR в выбранной области появляется запрос на ревью. Sloppy запускает агента с актуальным диффом, агент оставляет результаты в чате PR. В GitHub можно также подписаться на открытие или вывод из draft чужих PR в выбранном репозитории.
2. К своему открытому PR приходит новое замечание или содержательный ответ в треде. Sloppy продолжает существующий рабочий чат PR. Агент проверяет замечание и либо готовит правку в рабочей копии PR и запускает тесты, либо готовит ответ в том же треде. Публикация ответа, отправка ревью и push на пилоте проходят через действующий механизм подтверждения Sloppy.

## Что уже есть

- Core умеет [переоткрывать и привязывать чат к PR](../../../Sources/sloppy/CoreService+CodeReviewSessions.swift) и [запускать workflow из проектной автоматизации](../../../Sources/sloppy/CoreService+Automations.swift). [Ручная отправка замечаний агенту](../../../ClientNative/Sources/SloppyClientCore/CodeReviewWorkspace.swift) даёт готовый путь передачи контекста и подтверждения приёма сообщения.
- GitHub-провайдер [читает свои PR, запросы на ревью и три вида комментариев](../../../Sources/sloppy/CodeReview/GitHubCodeReviewProvider.swift). [Существующий webhook GitHub Task Sync](../../../Sources/sloppy/CoreService+TaskSync.swift) отвечает за синхронизацию задач. Обработка событий PR описана в [прежнем плане Automations](../../superpowers/plans/2026-06-28-automations.md#task-4-add-cron-webhook-and-github-trigger-ingestion).
- Контракт [`SourceControlProvider`](../../../Sources/PluginSDK/SourceControlProvider.swift) сейчас покрывает репозитории, рабочие деревья и диффы. В Node-плагинах вызовы идут через [`NodeSourceControlProvider`](../../../Sources/sloppy/SourceControl/NodeSourceControlProvider.swift).
- Установленный `arcadia-code-review` уже читает свои PR, дифф и комментарии. Его каталог в рабочей копии `SloppyPlugins` пока не отслеживается Git. При переносе нужной логики в `arcadia-source-control` нужно сверить её с установленной версией и сохранить соседние изменения.

## Граница Core и плагина

**Все операции с Arc и Arcanum принадлежат `arcadia-source-control` в `SloppyPlugins`.** Плагин сам читает данные о PR, проверяет авторство и назначения, переводит ответы Arcanum в общий формат и публикует подтверждённый ответ. В Core остаются выбор Source Control-провайдера проекта, расписание, хранение курсора, дедупликация, запуск агента и подтверждение публикации.

Предлагаемое расширение `SourceControlProvider` состоит из трёх необязательных операций, каждая объявляется отдельной capability.

| Операция | Контракт |
|---|---|
| `pollPullRequestEvents` | Принимает репозиторий, область наблюдения, виды событий и непрозрачный курсор. Возвращает нормализованные события и следующий курсор для полностью обработанной страницы. |
| `getPullRequestContext` | Принимает идентификатор PR и при необходимости ревизию. Возвращает состояние PR, ссылки, доступный контекст замечания и дифф в заданном лимите. Переиспользует общие модели Code Review. |
| `replyToPullRequestComment` | Принимает идентификаторы PR и комментария и подтверждённый текст. Возвращает ID и ссылку опубликованного ответа. |

Core вызывает операции по capability. Для старых плагинов новые операции недоступны до обновления. При недоступном плагине подписка показывает ошибку подключения. Идентификаторы уже привязанных к PR чатов проверяются при переходе на новый контракт. Для GitHub встроенный адаптер преобразует webhook в тот же формат событий.

## Границы и проверка каждого PR

### 1. Контракт Source Control

- Добавить общие Swift-модели, capabilities и операции [`SourceControlProvider`](../../../Sources/PluginSDK/SourceControlProvider.swift). Прокинуть их через Node JSON-RPC (`source_control.*` для v2) и проверить Swift-обёртку. Использовать дефолтный `unsupportedOperation` для провайдеров без поддержки. Описать контракт в [руководстве по плагинам](../../guides/plugins.md#source-control-plugins).
- Проверить на тестовом плагине сериализацию, прохождение ошибок, сохранение непрозрачного курсора, распознавание неполной страницы и загрузку старых провайдеров. Формат события и курсора не зависит от Arc, Arcanum или GitHub.

### 2. Передача события в чат

- Ввести два типа событий — запрос ревью и новая обратная связь. Хранить провайдера, репозиторий, PR, автора события, ссылку, внешний ID комментария или запроса и ревизию, к которой относится событие. Текст PR и комментарии передавать агенту как контекст задачи. Выбор агента, проекта и разрешённых действий брать из настроек подписки.
- Использовать существующий путь приёма сообщений с подтверждением и стабильным ключом запроса. Сохранять запись о событии до передачи в агентскую сессию и сохранять факт приёма после её подтверждения. При перезапуске сверяться по тому же ключу, включая сбой между приёмом сообщения и записью результата. Если штатная дедупликация запроса не покрывает этот интервал, закрыть его в этом срезе.
- Для замечания к своему PR переиспользовать рабочий чат с подходящим проектом и рабочей копией. При отсутствии или неоднозначности привязки создать чат для разбора и показать, что для правки нужна подтверждённая рабочая копия. Для чужого PR открыть или продолжить чат ревью. Одновременно выполнять один ход по одному PR. Новые события ставить в очередь.
- Проверить дубликат при конкурентной доставке, ошибку постановки, перезапуск после постановки, активный чат и выбор разных проектов для разных PR. Диагностика сообщает время, источник, итог доставки и ссылку на чат.

### 3. Подписка на Source Control-провайдера

- Добавить к проектным автоматизациям подписку с явным проектом, Source Control-провайдером, аккаунтом подключения, областью PR, интервалом и агентом. Хранить курсор Core по подписке и области. Продвигать его после надёжного сохранения полученных событий. Подтверждённый ответ направлять провайдеру, который поставил событие.
- Привязывать чат через общий идентификатор PR. Сверить существующие привязки `arcadia-code-review` при подключении `arcadia-source-control`. При необходимости задать совместимость идентификаторов в декларации плагина и обработать её общим кодом Core.
- Через тестовый плагин проверить отключение подписки, недоступность capability, частичную ошибку, повтор страницы и восстановление после рестарта.

### 4. Свои PR в Аркадии

- В `arcadia-source-control` переиспользовать реализацию чтения своих PR, замечаний и контекста из Arcadia-плагина ревью. Для пилота область задаётся выбранными PR, затем её можно расширить явным сопоставлением путей Аркадии. Идентичность автора и актуальность замечания проверяет плагин по данным Arcanum.
- При включении зафиксировать границу наблюдения. Первое чтение учитывает существующую историю и возвращает события после этой границы. Курсор плагина отражает обработанные комментарии по PR. Плагин исключает черновики, комментарии своего аккаунта и настроенных ботов и перепроверяет открытое состояние PR.
- На контролируемом PR проверить первое включение, новый ответ в старом треде, временную ошибку API, повтор опроса и перезапуск Core. Один новый комментарий даёт один ход в существующем чате. Отключение подписки останавливает новые запуски.

### 5. Чужие PR в Аркадии

- Проверка на живом PR подтвердила `arc pr list --reviewer <login> --no-draft --json` для назначений и `arc pr changes <ID>` для диффа. Плагин также читает комментарии своих PR через Arcanum. У списка Arc есть лимит, поэтому переполнение вызывает ошибку опроса и сохраняет курсор.
- `arcadia-source-control` возвращает новые назначения через `pollPullRequestEvents`. Первое включение фиксирует текущий список, следующее новое назначение запускает агентский ход один раз. Снятие запроса и повторное назначение разрешают новый запуск, когда источник позволяет различить назначения. Плагин пропускает черновики и PR вне области подписки.
- Проверить новым назначением на контролируемом PR. Агент получает ссылку и дифф актуальной ревизии, результат ревью виден в чате.

### 6. Подтверждённый ответ в Arcanum

- В `arcadia-source-control` переиспользовать операцию ответа Arcanum и объявить capability записи. Подтверждённый текст передаётся вместе с идентификатором исходного треда через общий контракт из PR 1.
- Проверить публикацию на тестовом PR и вернуть ссылку на отправленный ответ. После сетевого таймаута сверить результат с Arcanum перед повтором. Свой опубликованный ответ не запускает следующий ход агента.

### 7. GitHub

- Добавить отдельный вход событий PR в Core. Проверять `X-Hub-Signature-256` по исходному телу до обработки и сверять подключённый репозиторий. Подтверждать приём после долговременной записи события, запуск выполнять в фоне. [Проверка подписей GitHub](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries)
- Для чужих PR поддержать `pull_request` с `review_requested` и, при явном выборе, `opened` и `ready_for_review`. Для своих открытых PR обработать `pull_request_review` (`submitted`), `pull_request_review_comment` (`created`) и `issue_comment` (`created`, только для PR). Проверить, что одно замечание, пришедшее в событиях ревью и комментария, не передаётся агенту дважды. [События GitHub](https://docs.github.com/en/webhooks/webhook-events-and-payloads)
- Проверить неверную подпись, повтор доставки, посторонний репозиторий, собственный комментарий, закрытый PR и два рабочих сценария в тестовом репозитории. Для живой проверки потребуется HTTPS-адрес получателя, доступный GitHub.

### 8. Подтверждённый ответ в GitHub

- Добавить поддержку ответа на inline-замечание и комментария в общем обсуждении PR. После подтверждения использовать сохранённую связь черновика с PR и исходным замечанием.
- Проверить ссылку на опубликованный ответ, сверку результата после таймаута и исключение собственного ответа из событий обратной связи.

## Решения перед реализацией

- **Порядок интеграции** — сначала обратно совместимый контракт Source Control, затем общий путь событий и полностью подключаемые сценарии. Проектная подписка задаёт провайдера, агента и область наблюдения.
- **Область входящего ревью** — для пилота в Аркадии запросы на ревью конкретному пользователю. В GitHub по умолчанию так же, с возможностью включить открытие PR по репозиторию. Если для Аркадии нужны все новые PR по командным путям, источник для этой подписки проверяется отдельно при разведке PR 5.
- **Режим публикации** — агент автоматически готовит результат. Публикация ответов, отправка ревью и push в пилоте требуют подтверждения через штатный механизм Sloppy. Для этого плана достаточно конфигурации на стороне Core и существующего PR-чата.

## Готовность пилота

Для каждого провайдера проверить запуск ревью чужого PR и продолжение нужного чата после комментария к своему PR. На своём PR проверить обе развилки — правку с тестами и подтверждённый ответ в треде. Повтор события, перезапуск Core и собственный ответ не дают лишнего запуска. В каждом PR сначала пройти профильные тесты изменённого слоя, затем проверки из `AGENTS.md` для затронутых целей. Для `SloppyPlugins` прогнать тесты плагина отдельно.

Локально прошли 15 профильных Swift-тестов и 38 тестов плагина. На реальных PR Аркадии проверили чтение диффа назначенного ревью и списка комментариев к своему PR через JSON-RPC плагина. Полный прогон Swift завершился с 195 замечаниями, включая отказы песочницы при открытии локальных сокетов. Боевые подписки и отправка ответов остаются проверками пилота.
