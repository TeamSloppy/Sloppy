# Managed Sloppy Remote (invite-only v1)

The managed relay is a separate `SloppyRelay` executable. It must never expose
the full `sloppy` Core API, PostgreSQL, or port 25111 directly to the Internet.
It forwards only opaque E2E envelopes between authenticated devices in the same
personal space. The old personal relay on 25101/25102 is a separate service and
must remain running during migration.

## Local verification

Build and test from the repository root:

```sh
swift build --product SloppyRelay
swift test --filter ManagedRelay
```

The PostgreSQL integration test runs only when
`SLOPPY_RELAY_TEST_DATABASE_URL` names a dedicated database whose name begins
with `sloppy_relay_integration`. Use a fresh database for each run; the test
enrolls a one-time first admin and two spaces.

`SloppyRelay serve` requires `--public-url https://...` and exactly one of
`--database-url` (development only) or `--database-url-file`. In deployments,
set `SLOPPY_RELAY_PEPPER_FILE` to a mounted secret containing at least 32 random
bytes encoded as base64. Do not reuse either the database credential or pepper
between test and production. Keep all secret files outside the repository.

## Isolated Compose projects

`utils/docker/relay-compose.yml` sets the project name from `RELAY_ENV`, so
`test` and `prod` get different database networks and volumes. Supply immutable
image digests with `RELAY_IMAGE` and `RELAY_POSTGRES_IMAGE`; supply separate
secret file paths with `RELAY_POSTGRES_PASSWORD_FILE`,
`RELAY_DATABASE_URL_FILE`, and `RELAY_PEPPER_FILE`. The DB URL secret must refer
to the Compose-local `postgres` host and `relay` database. Set
`RELAY_PUBLIC_URL` to the corresponding HTTPS hostname. Compose does not publish
PostgreSQL or relay ports; only its frontend network is for the shared edge.

Before any deployment, configure DNS-only A records for
`relay-test.sloppy.team` and `relay.sloppy.team` pointing to `81.26.176.106`.
The existing edge Caddy must be attached to both
`sloppy-relay-test-frontend` and `sloppy-relay-prod-frontend` and route those
hostnames to `relay:25111` on the respective networks. Verify ACME certificates
and a WSS upgrade through the edge before enrolling a real device. Do not add
public port mappings as a workaround for missing DNS or edge routing.

Bootstrap the first admin only with `SloppyRelay bootstrap-admin` on the VPS,
using the public key generated by `/admin` in the target environment and the
same environment's mounted DB URL and pepper. The browser's non-exportable
private key remains in its WebCrypto storage. Do not bootstrap a production
admin from a test browser key.

## Promotion gates

1. Build one immutable relay digest; validate Compose and migrations against an
   empty and an existing test database.
2. Verify `/healthz`, `/readyz`, unauthenticated management denial, signed
   admin login, invite consumption/replay, QR claim/host approval, WSS encrypted
   RPC, cross-space denial, host-offline response, revoke, and reconnect.
3. Verify physical and logical PostgreSQL backups, 14-day retention, SHA-256
   manifests, and a restore smoke before production deployment.
4. Promote the exact tested image digest to production, with separate DB,
   volume, pepper, admin key, and edge route. Keep the previous digest available
   for rollback. Never import legacy `MeshState` into a managed space.

Production promotion is **not** justified by a successful Swift build or local
relay readiness check alone.

The maintenance profile runs `scripts/relay-backup.sh` in an isolated PostgreSQL
client container. It writes physical and logical backups, starts temporary
physical and logical restores without published ports, verifies both can query
`personal_spaces`, writes SHA-256 checksums, and retains 14 days. The
`utils/systemd/sloppy-relay-backup@.timer` template schedules this daily for
each environment; install/enable it only after a manual test backup and restore
smoke succeeds on the VPS. The named `relay_backups` volume belongs to exactly
one Compose project, so test and production backups never share storage.
